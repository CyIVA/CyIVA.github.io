# 개발자 블로그 요구사항 명세 및 개발 계획

작성일: 2026-09-05 · 버전: 0.4 · 상태: 기술 스택·운영 방식·디자인 방향 확정

이 문서는 사용자가 요청한 필수 기능과 구현을 위한 권장 기본값을 구분한다. 이번 작업 범위는 계획 수립이며, 콘텐츠 변경·앱 구현·배포는 수행하지 않는다.

## 1. 목표와 범위

기존 Markdown 콘텐츠를 계속 작성·관리할 수 있는 개인 개발자 블로그를 새로 구축한다. 글 탐색, 카테고리별 글 확인, 날짜 중심 연혁을 핵심으로 한다.

확정 운영 원칙: **기존 글의 Liquid 의존성은 초기 구축 때 한 번 정리하고, Astro로 사이트를 구성한 뒤에는 Markdown만 추가한다.** 일상적인 글 게시와 새 카테고리 추가에는 사이트 코드·라우팅·설정을 수정하지 않는다. 기존 데이터 호환은 내용과 메타데이터를 보존하는 의미이며, 기존 Liquid 실행 방식을 계속 유지하는 것은 아니다.

- 필수: 기존 포스트·연혁·프로젝트 데이터 호환, 카테고리 팝업, 카테고리별 글 수, 이전·다음 글, 연혁 날짜 구조 변경, 라이트/다크 토글, 마우스 반응형 dot matrix 홈, 프로젝트 소개 팝업, 콘텐츠 공개 여부 설정.
- 권장 기본 구성: 홈, 포스트 목록·상세, 연혁, 프로젝트 목록·소개 팝업, 모바일 대응, 기본 검색엔진 메타데이터.
- 후속 후보: 전체 글 검색, 목차, 댓글, RSS, 카테고리별 자동 색상. 이전 글에 소개된 기능은 자동으로 신규 요구사항에 포함하지 않는다.

호환 설계에 영향을 주는 확인 사항:

1. 실제 필드명은 `categories`다. 사용자가 말한 “categories 안의 tag”는 이 배열의 개별 카테고리 항목으로 해석한다. 별도 `tags` 필드도 존재하므로 둘을 자동으로 합치지 않는다.
2. `jekyll/Jekyll`, `javascript/JavaScript`, `css/CSS`, `dev/Dev`처럼 대소문자가 섞여 있다.
3. 본문에 `{% post_url ... %}`, `{% raw %}`, `{% highlight css %}` 등 Jekyll/Liquid 문법이 남아 있다. 일반 Markdown 로딩만으로는 호환이 완료되지 않는다.
4. `2025-12-07-history-page-update copy.md`의 메타데이터 날짜는 `2025-12-08`이다. 화면 날짜와 정렬에는 메타데이터를 사용해야 한다.
5. 파일명에 공백과 `copy`가 있고, 제목이 같은 글도 있다. 제목만으로 콘텐츠를 식별하면 안 된다.
6. 외부 이미지 링크가 있다. 이 폴더에는 이미지 파일이 없으며, 외부 이미지의 실제 접근 가능 여부는 아직 검증하지 않았다.
7. 기존 공개 URL은 유지하지 않기로 확정했다. 새로운 URL 규칙을 적용하고 본문의 내부 링크도 새 주소로 변환한다.

## 3. 확정 기술 스택

**Astro + HTML/CSS + JavaScript + GitHub Pages + GitHub Actions**를 사용한다. 콘텐츠는 일반 Markdown 본문과 YAML frontmatter로 관리한다.

| 기술 | 역할과 선택 이유 |
| --- | --- |
| Astro | Markdown 컬렉션을 읽어 각 페이지를 정적 HTML로 생성한다. HTML과 유사한 템플릿에서 JavaScript를 사용하므로 사용자의 경험을 활용하기 좋다. |
| Vite | Astro의 개발 서버·빌드 기반으로 활용한다. 별도 Vite 앱을 이중으로 구성하지 않는다. |
| CSS | 기본 CSS와 공통 스타일 변수로 시작한다. 초기 단계에서 별도 UI 프레임워크를 필수로 두지 않는다. |
| JavaScript | 팝업과 목록 필터 등 브라우저 상호작용을 담당한다. React나 Vue는 초기 필수 의존성이 아니다. |
| Node.js/npm | 개발·빌드 환경에 사용한다. 버전은 구현 시 Astro 지원 범위에 맞춰 고정한다. |
| GitHub Actions / Pages | 콘텐츠 변경을 빌드하여 정적 결과물을 기존 github.io 호스팅 방식으로 배포한다. |
| Traefik | 서버 앞에서 요청을 중계하는 프록시다. 현재 정적 Pages 배포에는 도입하지 않으며, 향후 자체 서버/API 운영 시 재검토한다. |

Astro는 콘텐츠 컬렉션과 정적 페이지 생성을 지원하고 GitHub Pages 배포 절차를 제공한다. [콘텐츠 컬렉션 공식 문서](https://docs.astro.build/en/guides/content-collections/), [GitHub Pages 배포 문서](https://docs.astro.build/en/guides/deploy/github/)

Vite 설정은 Astro 설정을 통해 조정할 수 있다. Traefik은 애플리케이션 프록시 역할의 도구다. [Astro 설정 문서](https://docs.astro.build/en/reference/configuration-reference/), [Traefik 공식 문서](https://doc.traefik.io/traefik/)

초기 구축에서 컬렉션 로더와 공통 상세 페이지 생성 경로를 한 번 구성한다. 이후 추가된 글의 페이지는 빌드 시 자동 생성한다. Liquid 실행기나 반복적인 레거시 변환 계층은 운영 의존성에 포함하지 않는다.

### 4.1 카테고리 동작 기본값

- `categories`를 집계와 팝업의 기준으로 사용한다. `tags`는 원본 메타데이터로 보존하되 이번 카테고리 집계에 포함하지 않는다.
- 권장: 집계 키는 앞뒤 공백 제거 및 대소문자 통일로 생성한다. 예를 들어 `Jekyll`과 `jekyll`을 한 그룹으로 묶되 원본 파일은 변경하지 않는다.
- 표시 이름은 별도 매핑으로 `Jekyll`, `JavaScript`, `CSS` 등 일관되게 지정하고, 등록되지 않은 이름은 최초 표기를 사용한다.
- 한 글에 같은 카테고리가 중복되어도 그 카테고리의 글 수는 1개만 증가한다. 여러 카테고리에 속한 글은 각각에 포함하므로 카테고리별 건수의 합이 전체 글 수와 같을 필요는 없다.
- 팝업은 해당 카테고리의 공개 글을 최신순으로 표시한다. 현재 읽는 글도 포함하고 현재 글임을 표시한다.
- 팝업은 새 브라우저 창이 아닌 페이지 내부 모달로 구현한다. 닫기 버튼·Escape·바깥 영역 클릭으로 닫히고, 닫은 뒤 실행 버튼으로 키보드 초점을 돌려준다. 열린 동안 초점이 모달 안에서 이동한다.
- 긴 목록은 팝업 내부에서 스크롤한다. 모바일에서는 화면 폭에 맞춘다.
- 전체 목록의 카테고리는 이름순으로 나열한다. 선택하면 같은 팝업을 여는 동작을 기본안으로 하여 화면 간 동작을 통일한다.
- 카테고리가 없는 글도 전체 목록에 남긴다. 카테고리 항목은 실제 데이터에 있는 값으로 구성한다.

### 4.2 글 정렬과 이전·다음 글

- `date` 내림차순이 전체 목록과 팝업의 기본 정렬이다.
- 같은 날짜는 원본 상대 파일 경로의 오름차순으로 순서를 고정한다. 이 순서는 최신순 표시 기준이며, 이전·다음 연결은 그 목록을 역순으로 만든 시간순 목록에서 계산하여 동률 처리도 일치시킨다.
- 이전 글은 공개 글의 전체 시간순에서 앞선 글, 다음 글은 뒤따르는 글이다. 카테고리에 따라 대상이 달라지지 않는다.
- 같은 날짜의 글은 위 보조 정렬로 인접 순서를 정한다. 가장 오래된 글에는 이전 링크, 가장 최신 글에는 다음 링크를 표시하지 않는다.
- 날짜만 있는 값은 달력 날짜로 처리하여 시간대 변환으로 하루가 바뀌지 않게 한다. 공통 화면 표시 형식은 `YYYY.MM.DD`를 기본안으로 한다.

### 4.3 연혁

목표 데이터 형식:

```yaml
---
title: Unity Dev
date: 2015-12-01
---
Started Unity Development.
```

- 단일 세로 목록에 연도별 구분과 날짜별 항목을 둔다. 간격은 실제 기간 길이가 아닌 콘텐츠 높이에 맞춘다.
- 최신 날짜가 위에 오도록 배치하고 같은 날짜는 파일 경로 순으로 고정한다.
- 본문이 없어도 날짜와 제목만으로 정상 표시한다.
- 이 변경은 `_history`에만 적용한다. 프로젝트의 `start_date/end_date`는 현재 요구에서 변경 대상이 아니다.
- 구현 단계에서 연혁 9개 파일을 명시적으로 변환한다. 전환기 로더는 `date`가 없을 때 `start_date`를 임시로 읽을 수 있으나, 최종 데이터 검증에서는 새 스키마를 요구한다.
- 두 날짜 필드가 함께 있고 값이 다르면 자동 선택하지 않고 파일명을 포함한 검증 오류를 낸다. 변환 후 제목·본문과 기존 시작 날짜가 보존되는지 확인한다.

## 5. 일회성 콘텐츠 변환과 자동 게시 설계

### 5.1 초기 구축에서 한 번 수행할 변환

변환 흐름: **Git 이력 또는 백업으로 복원 지점 확보 → URL 확정 → Liquid 의존 문법을 일반 Markdown으로 변환 → 렌더링·링크 검증 → 변환 완료본을 콘텐츠 원본으로 사용**.

1. `all_collections`를 유일한 콘텐츠 원본으로 삼고 다른 폴더에 Markdown을 수동 복제하지 않는다. 변경 파일과 변환 내용을 기록하고 제목·날짜·카테고리·별도 tags·본문 의미를 보존한다. 본문 변환은 이관 시 한 번 수행하며 정기 빌드에서는 실행하지 않는다.
2. `layout: post`는 포스트·프로젝트의 일회성 변환에서 제거한다. 화면 템플릿은 Astro에서 컬렉션 종류로 선택하고 신규 글 양식에 `layout`을 요구하지 않는다.
3. 문서 식별자는 컬렉션과 원본 상대 경로를 기준으로 만든다. 표시 제목과 URL 식별자를 분리한다.
4. 글 URL은 `/posts/<파일명에서 파생한 고유 slug>/`를 기본안으로 한다. 공백 처리와 중복을 검증하여 링크 변환 전에 URL을 확정한다. 필요하면 선택적 `slug` 메타데이터로 주소를 고정할 수 있게 한다. 신규 글에 별도 URL 매핑 등록을 요구하지 않는다.
5. `{% post_url ... %}`는 참조 글의 확정 URL을 사용하는 일반 Markdown 링크로 바꾼다. 대상을 찾지 못하면 파일과 위치를 보고하고 이관 완료 전에 해결한다.
6. `raw/endraw` 렌더링 래퍼를 제거하고 내부 예제 문자열을 보존한다. `highlight/endhighlight`는 언어가 지정된 fenced code block으로 바꾼다. 코드 안에 설명용으로 적힌 Liquid는 그대로 표시하고 실행하지 않는다.
7. 전역 문자열 치환만으로 처리하지 않고 코드 블록·인라인 코드·본문 문맥을 구분한다. 변환 후 실행이 필요한 Liquid 문법이 남지 않았는지 검증한다. 변환 도구는 이관용으로 보관할 수 있으나 정기 빌드에 연결하지 않는다.
8. 일반 Markdown 표·목록·인용·코드·이미지를 지원한다. 코드 안 HTML은 예제로 표시하며 실행하지 않는다.
9. 외부 이미지 URL은 유지한다. 내부 링크와 로컬 자산 경로는 빌드 결과 기준으로 검증하고, 외부 링크·이미지는 별도 접근 확인 목록을 만든다.
10. 이전 공개 URL 보존과 리디렉션은 구현 범위에서 제외한다. 새 URL 규칙과 변환된 내부 링크의 일관성을 검증한다.

### 5.2 이후 자동으로 수행할 빌드·게시

**Markdown + YAML 메타데이터 → Astro 컬렉션 검증 → 정적 HTML·목록·카테고리 인덱스 생성 → GitHub Pages 배포**.

- 모든 포스트를 읽어 상세 페이지와 전체 목록, 카테고리별 건수·팝업 데이터, 이전·다음 글 연결을 함께 갱신한다. 파일별 라우트와 별도 콘텐츠 목록을 수동 등록하지 않는다.
- 새 카테고리는 글의 `categories`에 적으면 자동 등록된다. 표시 이름 매핑은 선택 사항이며 등록하지 않아도 기본 표기로 정상 동작한다.
- GitHub Actions는 게시 브랜치의 콘텐츠 변경에도 실행된다. GitHub 파일 업로드 후 커밋 또는 로컬 커밋·push로 배포를 시작한다. 로컬 폴더에 저장만 한 상태는 공개 게시가 아니다.
- 필수 메타데이터 오류, 중복 URL, 끊어진 내부 링크는 배포 전에 검출한다. 실패한 빌드는 배포하지 않는다.

### 5.3 글 작성 양식과 운영 안내

파일 예시: `all_collections/_posts/2026-09-05-new-post.md`

```markdown
---
title: 새 개발 기록
date: 2026-09-05
categories: [JavaScript, Blog]
---

## 오늘 구현한 내용

여기에 일반 Markdown으로 본문을 작성합니다.
```

운영자는 파일 작성 → GitHub 커밋 → 자동 배포 결과 확인 순서로 게시한다. 한국어 안내에 복사 가능한 작성 양식, 파일명·메타데이터 규칙, 이미지·글 링크 작성법, 배포 상태와 오류 확인법을 포함한다. 글 작성에 Astro 문법을 요구하지 않는다.

사이트 코드는 기능·디자인 변경 시 수정한다. 개발 환경과 의존성 버전을 고정하고 불필요한 플러그인을 줄인다. 배포 환경·의존성 변화에 따른 간헐적 점검 가능성은 있으나 일상 게시에는 코드 변경이 필요 없어야 한다.

## 7. 품질 기준

- 주요 본문과 링크는 정적 HTML로 제공하여 JavaScript 실행 전에도 읽을 수 있게 한다. 카테고리 링크는 JS가 없으면 해당 카테고리의 정적 목록으로 이동하는 대체 경로를 제공한다.
- 모바일 360px부터 데스크톱까지 본문이 화면을 넘지 않아야 한다. 긴 코드와 표는 자체 영역에서 가로 스크롤한다.
- 팝업 실행과 닫기, 글 이동을 키보드만으로 수행할 수 있어야 한다.
- 페이지별 제목·설명·canonical을 제공하고, 존재하지 않는 경로에 대한 404 화면을 준비한다.
- 잘못된 필수 필드·날짜·중복 URL·끊어진 내부 글 참조는 배포 전 검증에서 발견한다.
- 빌드 실패 시 배포 단계를 실행하지 않는다. 게시된 상세 URL에 직접 진입하거나 새로고침해도 정상적으로 열린다.

일회성 변환 결과와 자동 페이지 생성을 먼저 검증한 뒤 본격적인 화면 구현을 진행한다. 지금 일정은 단계 순서 기준이며, 화면 디자인과 추가 기능 범위가 정해진 뒤 작업량을 추정한다.

핵심 검증 사례:

- `jekyll/Jekyll`의 통합 결과와 중복 카테고리 건수, 별도 `tags` 미포함 확인.
- 팝업의 제목 링크, Escape 닫기, 초점 복귀, 모바일 긴 목록 확인.
- 날짜가 같은 글, 최초·최신 글, 파일명 날짜와 메타데이터 날짜가 다른 글의 순서 확인.
- 기존 `post_url` 링크가 실제 글로 연결되고 `raw/highlight` 변환 후 코드 예제가 보존되는지 확인. 설명용 코드 외에 실행을 요구하는 Liquid 문법이 남지 않았는지 검사.
- 연혁 변환 전후 항목 수·제목·본문·시작 날짜 동일성 및 새 스키마 확인.
- 전체 상세 페이지 직접 진입, 생성 URL 중복과 끊어진 내부 링크 검사.

- 검증 환경에서 새 카테고리가 포함된 Markdown 한 개만 추가하여 상세 페이지·목록·건수·팝업·이전/다음 글이 모두 갱신되는지 확인. 테스트 글은 공개 콘텐츠에 남기지 않는다.
- 게시 워크플로에서 정상 커밋의 자동 배포와 잘못된 메타데이터의 배포 차단을 확인한다.

## 9. 확정 사항과 다음 논의

Astro 사용, 초기 Liquid 의존성 제거, 이후 Markdown 업로드 기반 자동 게시 운영은 사용자 확정 사항이다.

카테고리 대소문자 통합, 팝업에 현재 글 포함, 전체 글 기준 이전·다음 이동, 날짜 표시 형식, 연혁 최신순, 팝업 주소 표현 방식은 이 문서의 권장안이다. 아직 사용자 확정 사항으로 간주하지 않는다.

디자인과 운영에 대한 추가 확정 사항은 10~12절에 정리한다. 다음 작업은 이를 바탕으로 PC·모바일의 홈, 글 목록·상세, 프로젝트 팝업 시안을 구체화하는 것이다. 소개 문구와 프로젝트별 설명·이미지는 콘텐츠 보완 항목이며, 구조 설계를 막지 않는다.

- 소개 문구는 아직 미제공이다. 시안용 임시 문구는 “개발 과정과 프로젝트를 기록하는 원민철입니다.”로 두고 확정 문구와 구분한다. 경력·기여·성과를 추정하여 작성하지 않는다.

### 10.1 테마 토글

라이트/다크 두 상태의 토글을 공통 헤더에 둔다. 기본안은 첫 방문에 운영체제 설정을 따르고, 직접 선택한 이후에는 저장된 선택을 우선하는 것이다. 페이지 이동·새로고침·재방문에도 유지하며 첫 화면에서 반대 테마가 잠깐 보이는 현상을 방지한다. 저장소 사용이 불가능해도 전환 기능은 동작해야 한다.

### 10.2 Dot matrix 동작 기본안

포인터 주변 점들이 작은 범위에서 부드럽게 밀려나거나 밝기가 변하고, 포인터가 벗어나면 제자리로 돌아온다. 소개 카드의 읽기·클릭을 방해하지 않게 장식 레이어로 배치한다. Canvas 기반으로 구현하고 새 그래픽 프레임워크를 필수로 추가하지 않는다.

모바일처럼 마우스가 없는 환경과 `prefers-reduced-motion` 환경에서는 정적인 점 패턴을 제공한다. 화면 밖이나 비활성 탭에서는 애니메이션을 멈추고, 점 개수·해상도에 상한을 둔다. JavaScript가 없어도 소개와 링크는 읽고 사용할 수 있어야 한다.

## 11. 프로젝트 소개 팝업과 콘텐츠 보완

홈의 대표 프로젝트 카드와 프로젝트 목록 카드를 선택하면 동일한 소개 팝업을 연다. 팝업 안의 명시적인 프로젝트 링크로 GitHub에 이동한다.

팝업 구성: 제목 → 간단한 소개 → 사용 언어·프레임워크 → 관련 사진 → 프로젝트 링크. 기존 기간·본문이 있으면 보조 정보로 보존하여 표시한다. 키보드 초점 관리, Escape·닫기 버튼·바깥 영역 클릭, 모바일 내부 스크롤은 카테고리 팝업과 동일하게 적용한다. JavaScript 비활성 상태에는 프로젝트 목록에서 소개·링크를 정적으로 펼쳐 제공한다.

프로젝트 Markdown에 추가할 필드:

| 필드 | 의미 | 호환 기본값 |
| --- | --- | --- |
| `languages` | 사용 언어 배열 | 빈 배열 |
| `frameworks` | 사용 프레임워크 배열 | 빈 배열 |
| `description` | 간단한 소개 | 기존 값 또는 본문 요약 |
| `images` | `src`, `alt`를 가진 이미지 배열 | 빈 배열 |
| `links` | `label`, `url`을 가진 프로젝트 링크 배열 | 빈 배열 |
| `featured` | 홈 대표 프로젝트 노출 여부 | false |
| `published` | 사이트 게시 여부 | true |

기존 샘플은 추가 정보가 없어도 정상적으로 열린다. 빈 항목은 숨기고 사진이 없으면 이미지 영역을 생략한다. 제공된 두 실제 프로젝트는 기존 샘플과 별도 항목으로 추가하고 `featured: true`로 지정한다. 기존 원본 26개 보존 검증과 신규 프로젝트 추가 건수를 구분한다.

사용자가 제공한 저장소 URL은 확정 링크로 보존한다. 구체적인 언어·프레임워크·사진·기여 설명은 저장소 자료와 사용자 제공 자료를 확인하여 채운다. 이번 조사에서 HeimerRuri 페이지는 열렸지만 Procedural-Terrain은 웹 도구 오류로 내용 확인이 되지 않았다. 해당 링크를 삭제하거나 존재하지 않는다고 판단하지 않는다.

## 12. 공개·비공개 운영 정책

포스트·프로젝트·연혁에 선택적 boolean 필드 `published`를 공통으로 지원한다. 누락 시 true로 처리하여 현재 테스트 글과 샘플 프로젝트도 모두 공개한다. 게시를 중단하려면 해당 Markdown에 아래 값을 넣고 커밋한다.

```yaml
published: false
```

- 빌드에서 공개 콘텐츠만 먼저 추린 뒤 HTML·목록·카테고리 집계·팝업 데이터·이전/다음 글·홈 대표 프로젝트를 생성한다. CSS나 브라우저 필터로 감추는 방식은 사용하지 않는다.
- 비공개 포스트는 직접 URL로 접근해도 생성된 페이지가 없어야 한다. 공개 상태로 되돌리면 같은 URL로 다시 생성된다.
- 사이트맵 및 향후 추가하는 검색 인덱스·RSS에도 동일한 공개 필터를 적용한다. 전체 빌드 산출물을 교체하여 이전 배포 파일이 남지 않게 한다.
- 공개 글 본문에서 비공개 글로 향하는 수동 링크는 검증 오류로 알리고 배포 전에 수정한다. 비공개 전환 커밋의 배포가 성공해야 실제 사이트에서 내려간다.
- 이 기능은 사이트 게시 제외다. 공개 GitHub 저장소에 있는 원본과 Git 이력, 이미 배포·복사된 자료까지 비밀로 만드는 접근 제어 기능은 아니다. 원본 Markdown을 사이트 배포 파일로 복사하지 않는다. `public/`에 둔 이미지는 직접 접근 가능한 공개 자산으로 취급한다.

추가 개발·검증 항목:

1. 화면 설계 단계에 라이트/다크 홈, dot matrix, 소개 카드와 프로젝트 팝업을 포함한다.
2. 홈·연혁·프로젝트 구현 단계에 테마 토글, dot matrix, 프로젝트 메타데이터 확장과 대표 프로젝트 2개 등록을 포함한다.
3. 자동 게시 구현 단계부터 공통 공개 필터를 적용한다. 공개→비공개→공개 전환 시 생성 파일·클라이언트 데이터·집계·직접 URL 결과를 검증한다.
4. 테마 선택 유지, 첫 렌더링, 키보드 팝업 조작, 모바일·동작 줄이기 설정에서 정적 dot matrix를 확인한다.
